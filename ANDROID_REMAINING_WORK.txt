GlowUp AI Android — Remaining Work Handoff
===========================================

Scope
-----
This handoff follows ANDROID_PLAN.md as the source of truth. It intentionally excludes:
- Production hardening and Play Store release work.
- Backend deployment/hosting/CI and environment-secret setup.
- Firebase project configuration and authentication-provider work.

The app is a substantial Android rebuild, but it is not production-ready yet. Existing source
presence must not be treated as completion: several areas still need compile verification, tests,
state audits, and end-to-end API validation.

Current progress
----------------
Completed or substantially implemented in the Android tree:

1. Architecture and design system
   - Compose feature packages exist for auth, onboarding, home, capture, routine, insights,
     discover, account, and the shared shell.
   - Honey/Bumble-adjacent tokens, light/dark themes, spacing, shapes, motion, reusable cards,
     buttons, fields, error/empty/locked states, metric components, bottom navigation, and
     previews exist.
   - The original all-in-one MainActivity/legacy screen path has been replaced by feature-owned
     screens and navigation graphs.

2. Backend contract surface
   - GlowUpApi.kt covers the complete documented backend route family, including health, session,
     profile/consent, subscriptions, products, routine events, captures, dashboard/history,
     engagement/check-ins/recap/analytics, Q&A/triage, discover/commerce, labels, reprocessing,
     shelf scan, context/root-cause/budget/derm export, export/deletion, and admin declarations.
   - DTO-to-domain mapping and centralized API error normalization exist.
   - 204 deletion handling, 403 Premium/consent errors, capture quality coaching, queued jobs,
     and backend field-name mismatches have been addressed in the data layer.

3. Persistence, repositories, and background work
   - DataStore session identity and cached entitlement/onboarding/consent/reminder state exist.
   - Room cache/outbox structures exist for dashboard/history/product-related data and offline
     capture upload.
   - Domain repositories exist for session, home, capture, routine, experiments, insights,
     discover, billing, and privacy.
   - WorkManager capture outbox processing and server-driven reminder scheduling/notifying exist.
   - Mutation locks, request deduplication, cache invalidation signals, and telemetry queue
     infrastructure exist.

4. Session and navigation flow
   - SessionStateMachine is implemented and unit-tested at the domain level.
   - Splash health check, Firebase-session handoff, profile classification, onboarding/consent,
     baseline-needed, ready, stale-user, and unauthorized branches are represented.
   - Type-safe destinations and graphs cover all planned feature destinations.
   - MainActivity now injects SessionStore and Telemetry correctly.
   - Reminder notification action routing now carries an explicit open-capture request through the
     activity and opens Capture only after the workspace route is available.
   - Notification permission prompting is scoped to the Home route instead of app startup.

5. Network/app-shell corrections already made
   - Hilt now uses the single NetworkFactory client, including timeout, safe-GET retry policy,
     auth interceptor, and redacted debug logging.
   - Retrofit base URLs were aligned with the API annotations so the /api prefix is not doubled.
   - Release build configuration now enables minification and resource shrinking.
   - One malformed literal newline in CaptureScreen imports was corrected.

Known verification caveats
---------------------------
- Do not mark the app production-ready from source inspection alone.
- Android SDK installation, real Firebase credentials, production auth configuration, deployment,
  signing, CI, Play Console, privacy-policy/store assets, and release rollout are intentionally
  outside this handoff.
- Backend tests were previously observed green in an isolated temporary database environment;
  the repository's default old SQLite file can still have schema drift. That is a backend/runtime
  concern, not proof that the Android client is end-to-end verified.

Definition of Android completion (excluding the intentionally omitted work)
---------------------------------------------------------------------------
The Android portion is complete when:
- Debug and release compile cleanly.
- Every ANDROID_PLAN.md Phase 2–5 item above has a demonstrated implementation or test.
- Every backend route intended for the client is reachable from a real screen or covered by a
  repository/contract test.
- Free/Premium, consent, offline, empty, error, queued-job, and deletion behavior is explicit.
- The five critical Compose journeys pass without real Firebase/deployment dependencies.
- No known compile blocker, no-op user action, fake metric, or unverified endpoint family remains.
